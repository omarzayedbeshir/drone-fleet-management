# Normalized telemetry ingestion

This implements the NFR-05 validation, duplicate detection, rejection logging, and accepted-record consistency foundation. It does **not** complete NFR-05: audit integration for future mission/maintenance/role/organisation changes, off-server backups, and tested restore procedures remain pending.

Apply migrations through `000006_telemetry_ingestion.sql` before starting the updated API. Earlier migration files are unchanged. TimescaleDB must already be installed by migration 000001.

## Scope and access

`POST /api/v1/drones/{id}/telemetry` accepts one normalized sample for a drone in the authenticated fleet manager's organisation. It is a manual/testing ingestion endpoint using the existing session cookie and exact `Origin` check. Pilots, technicians, and system administrators cannot submit. Manager/pilot/technician accounts can read their own drone history with `GET /api/v1/drones/{id}/telemetry?limit=20&offset=0`; pagination has the registry bounds (limit 1–100, offset 0–1,000,000). Missing/foreign drone IDs return 404 without writing tenant rejection records.

`internal/telemetry.PostgresStore.Ingest` is also the normalized persistence boundary for future adapters. It expects server-trusted organisation/actor IDs and never performs vendor polling or grants access itself. DJI/MAVLink decoding, CSV file parsing, automatic feed credentials, buffering/retry workers, batching, dashboard notifications, and maintenance-rule processing remain separate work. There is no telemetry frontend or public vendor webhook in this change.

## Common schema

The machine-readable contract is [schemas/telemetry.schema.json](schemas/telemetry.schema.json), referenced by the [OpenAPI draft](openapi.yaml). Example:

```json
{
  "event_id": "flight-42-sample-17",
  "source": "dji",
  "observed_at": "2026-10-29T07:00:00Z",
  "status": "available",
  "flight_time_seconds": 7200,
  "battery_cycles": 12,
  "fault_flags": [],
  "battery_percent": 85,
  "latitude": 30.0444,
  "longitude": 31.2357,
  "altitude_m": 120,
  "speed_mps": 4.5
}
```

Required fields: event ID, source, observation timestamp, operational status, cumulative lifetime flight seconds, cumulative drone battery cycles, and explicit fault flags (empty array means no faults). These counters are **totals**, not per-message increments; battery-specific lifecycle records and counter-reset reconciliation are not implemented. Never sum repeated totals. A future adapter must map vendor data to these meanings, supply a stable event ID, and filter unsupported payload fields before submitting.

- `event_id`: stable source identifier, 1–128 ASCII letters/digits/underscore/dot/colon/hyphen; starts with a letter/digit.
- `source`: `dji`, `ardupilot`, or `csv`. Real vendor sources must match the registered vendor. CSV is a testing/fallback format and can normalize data for either vendor.
- `observed_at`: RFC3339 instant since 1970, at most five minutes in the future. Timezone offsets are accepted, converted to UTC, and truncated to PostgreSQL microsecond precision. `received_at` is generated by the database.
- `status`: `available`, `charging`, `in_mission`, `grounded`, or `unknown`.
- Counters: required nonnegative signed 64-bit JSON integers.
- `fault_flags`: required array, at most 32 entries; codes use letters/digits/underscore/colon/hyphen, 1–64 characters each. Entries are deduplicated and sorted.
- Optional/null measurements: battery percentage 0–100; latitude -90–90 and longitude -180–180 (both numeric or both absent/null); altitude -12,000–100,000 metres; speed 0–500 metres/second. NaN and infinities are invalid. Altitude means metres above mean sea level (MSL); adapters must send null if they cannot establish that datum rather than treating AGL as MSL.
- Unknown fields, including imagery/video/payload blobs, are rejected. One JSON object is accepted per request, with a 16 KiB body limit. JSON Schema describes the shape; runtime validation additionally enforces timestamp tolerance and cross-record consistency.

## Duplicate and ordering rules

Identity is `(organisation_id, drone_id, source, event_id)` across all time chunks. The receipt table stores a SHA-256 hash of the canonical normalized sample. Equivalent JSON ordering/whitespace, timezone offsets, and fault-code order produce the same fingerprint.

An identical retry returns 200 with `duplicate: true`, the original sample/receipt timestamp, and `latest_updated: false`. It creates no new sample/receipt, changes no totals, and does not advance telemetry freshness. Reusing the identity with different normalized content returns 409 and writes an `event_conflict` rejection. A different event at an already occupied drone observation timestamp returns 409 (`timestamp_conflict`), preventing ambiguous latest samples. Adapters must retain event IDs on retries.

Both immediate temporal neighbours are checked for monotonic flight seconds and battery cycles. A delayed sample is accepted only if its totals fit between earlier/later accepted observations. A new latest sample cannot reduce totals. Contradictions return 422 (`counter_regression`); they require explicit reconciliation rather than silently resetting counters.

## Transaction and safety rules

Each ingestion transaction locks the owned drone. It inserts the duplicate receipt and hypertable observation together, then updates the drone projection only if the observation is newer than `last_telemetry_at`. Late history never overwrites the latest status, totals, faults, or timestamp. Projection totals are copied from the snapshot; they are not incremented. An existing grounded status remains grounded even when a newer observation says available. Only a later maintenance workflow can clear that safety state.

Observation/receipt/projection failures roll back the entire acceptance. Concurrent retries, including separate API processes, serialize on the drone and are accepted once. Accepted observations and duplicate receipts reject ordinary UPDATE/DELETE/TRUNCATE. Drone deletion with accepted history fails with 409; organisation deletion cascades through telemetry history as allowed by the existing deletion policy.

The registry API includes read-only cumulative counters/fault flags. Raw sample status may differ from the grounded projection because grounding takes precedence. Freshness expiration to `unknown` is **not** implemented as a worker or read-time calculation yet; the observation timestamp is available to that future workflow.

## Rejections and responses

Validated owned-drone submissions that fail schema, vendor, duplicate-content, timestamp-collision, or counter checks write an append-only `telemetry_rejections` row. It stores actor, organisation/drone IDs, a fixed reason code, database timestamp, and SHA-256 of received bytes. Raw payloads and arbitrary parser errors are never retained. For oversized bodies, only the first 16 KiB + 1 byte is read/hashed, rather than buffering an unbounded body.

Rejection logging must commit before a validation response is returned. If logging fails, the endpoint returns 503. Invalid payloads create no accepted sample, receipt, projection update, or generic audit event. Authentication/origin/UUID/media-type/body-read transport failures are handled before normalized ingestion and do not create rejection rows. Benign exact retries are successful duplicates rather than rejections.

Fresh acceptance returns 201; exact retry returns 200:

```json
{
  "duplicate": false,
  "latest_updated": true,
  "sample": {
    "event_id": "flight-42-sample-17",
    "source": "dji",
    "observed_at": "2026-10-29T07:00:00Z",
    "status": "available",
    "flight_time_seconds": 7200,
    "battery_cycles": 12,
    "fault_flags": [],
    "battery_percent": 85,
    "latitude": 30.0444,
    "longitude": 31.2357,
    "altitude_m": 120,
    "speed_mps": 4.5,
    "received_at": "2026-10-29T07:00:01Z"
  }
}
```

History returns `samples: []` and `pagination: {limit, offset, has_more}`, ordered by observation time descending. Schema/value errors return 422; conflicting identities/timestamps 409; oversized bodies 413; storage failures 503. Rejection responses include `error` and `code`.

Accepted telemetry is its own immutable observation history; we do not duplicate every high-frequency sample into `audit_events`. Audits remain for domain operations such as registry changes and future maintenance/mission/role/organisation changes. Automatic telemetry-based maintenance actions must explicitly use the shared audit recorder when implemented.

## Verification

Go unit tests cover schema rejection and canonicalization. Database integration tests use real TimescaleDB in isolated schemas to verify ownership/roles, malformed and invalid records, exact/conflicting/concurrent duplicates, late arrival, counter ordering, sticky grounding, history pagination, append-only records, rollback on projection/rejection-log failures, and organisation deletion. Run all backend checks with `TEST_DATABASE_URL` set and `go test -race ./...`, followed by `go vet ./...` and `go build ./...`. CI's integration suite includes telemetry.
